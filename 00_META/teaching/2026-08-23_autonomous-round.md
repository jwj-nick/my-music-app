## 1. 쿼리 빌더 — 선택이 문장이 되는 과정

**파일: `10_app/app.js`의 `buildQuery(sel)`**

핵심 아이디어: 사용자가 고른 선택지들(`sel` 객체)이 함수 하나를 통과하면 완성된 프롬프트 문장이
나온다. RTL로 치면 `sel`은 포트 입력, 템플릿은 모듈 본체, 반환 문자열은 출력이다.

```
sel = { type: "links", target: "웬디", form: "방송 커버 영상",
        period: "1y", count: 10, today: "2026-08-23", hint: "KBS 위주" }
        ↓ buildQuery(sel)
"웬디"의 방송 커버 영상을(를) 웹에서 검색해줘. 기간: 2025-08-23 ~ 2026-08-23. 최대 10개.
각 항목을 정확히 이 형식의 한 줄로 써줘:
곡명 | 아티스트 | 채널/방송 | 날짜 | URL
확인된 것만 쓰고 추측 금지. 실제 URL 필수. ...
```

품질을 만드는 장치 3개, 왜 각각 필요한가:

1. **상대 기간 → 절대 날짜 변환** (`shiftYears`/`shiftMonths`). "최근 1년"이라고 쓰면 모델이
   "내 학습 데이터는 2024년까지라..."라고 회피할 수 있다(웬디 TOP10 실패의 정확한 원인).
   "2025-08-23 ~ 2026-08-23"이라고 쓰면 회피 여지가 없고 웹 검색을 하게 된다.
2. **출력 형식 계약** (`곡명 | 아티스트 | ... | URL`). 형식을 못박아야 응답을 코드로 파싱해서
   "+추가" 버튼을 달 수 있다. 형식이 없으면 답은 읽고 버리는 텍스트로 끝난다.
3. **추측 금지·출처 필수 명시**. LLM은 그럴듯한 가짜 URL을 만들 수 있다 — 명시적으로 금지하고,
   파싱 단계에서도 `https?://` 검증으로 이중 방어한다.

**날짜 함수가 `Date` 객체를 안 쓰는 이유**: `buildQuery`가 내부에서 `new Date()`를 읽으면
실행하는 날짜마다 결과가 달라져 회귀 테스트가 불가능해진다. 그래서 `today`를 인자로 받는다 —
`recommend()`의 `excludeIds`와 정확히 같은 패턴(decisions.md #18).

✋ 체크: `test_prompt.js` case 7이 "연 경계"를 테스트한다. 1월 15일에서 1개월 전이 왜 특별한
케이스인지, `shiftMonths`의 `while` 루프가 이를 어떻게 처리하는지 설명할 수 있는가?

## 2. 응답 파싱 — 방어적으로 읽기

**파일: `app.js`의 `parsePipeLines` → `parseLinkResults` / `parseDiscoverResults`**

LLM 응답은 계약을 어길 수 있다("찾은 결과입니다:" 같은 서두, 불릿 기호, 필드 누락).
파싱 전략은 "맞는 줄만 줍고 나머지는 조용히 버린다":

1. 줄 단위로 쪼갬 → 2. 불릿/번호 접두(`- `, `1. `) 제거 → 3. `|` 개수가 정확히 맞는 줄만 통과
→ 4. T1은 마지막 필드가 실제 URL(`https?://`)인지 추가 검증.

파싱이 0건이면? 원문을 그대로 (링크만 클릭 가능하게 해서) 보여준다 — 실패해도 사용자는
정보를 잃지 않는다. 이런 "우아한 강등(graceful degradation)"이 LLM 파이프라인의 기본기다.

✋ 체크: 응답에 "곡명 | 아티스트 | 채널 | 날짜 | URL없음"이라는 줄이 있으면 어디서 걸러지는가?

## 3. 행선지 파이프 — AI 응답이 앱 데이터가 되는 순간

**파일: `app.js`의 `exAddLinkEntry` / `exAddDiscoverEntry`**

파싱된 항목의 "+추가"를 누르면 기존 인앱 추가(1.5 마일스톤)와 똑같은 `localEntries` 경로로
새 엔트리가 생긴다. 새로 배울 것이 거의 없는 이유: **1.5에서 만든 3레이어(seed/overrides/local)가

- T1 항목 → `links: [{label: "KBS 더시즌즈 2026-03-14", url}]` 포함 track 엔트리.
  intent는 대상 아티스트가 컬렉션에 있으면 그 intent 상속(웬디→taste), 없으면 taste.
- T3 항목 → 추천 이유가 `note`에, 제안 태그가 `tags`에 들어간 explore 엔트리.

## 4. CSS 토큰 시스템 — 다크/라이트가 안 깨지는 구조

**파일: `10_app/style.css` 상단, 근거: `00_META/design_plan.md`**

색을 컴포넌트에 직접 쓰지 않고 **토큰(CSS 변수)** 으로만 쓴다. 테마는 토큰 재정의로 바뀐다.
가드가 3단인 이유 — 사용자 상태가 3가지라서:

| 상태 | 셀렉터 | 언제 |
|---|---|---|
| 시스템 따름 (기본) | bare `:root` (라이트) + `@media (prefers-color-scheme: dark)`의 `:root:not([data-theme="light"])` | `data-theme` 스탬프 없음 — OS 설정이 결정 |
| 명시적 다크 | `:root[data-theme="dark"]` | 토글로 다크 고정 |
| 명시적 라이트 | bare `:root`가 그대로 적용 | 토글로 라이트 고정 — `:not([data-theme="light"])` 가드가 미디어쿼리를 무력화 |

고전 버그: 어떤 색을 미디어쿼리 **안에서만** 정의하면, 시스템-라이트 사용자에게 그 색이
아예 정의 안 되어 "다크 글자가 라이트 배경에" 같은 깨짐이 생긴다. 그래서 규칙은
"모든 토큰은 bare `:root`에 완전한 라이트 값으로 먼저 정의".

토글 순환(시스템→다크→라이트→시스템)은 `mma_theme` localStorage — API 키와 같은 저장 방식.

✋ 체크: `--accent`가 라이트에선 `#B36A12`(진한 앰버), 다크에선 `#F0A93C`(밝은 앰버)로 다른
이유는? (힌트: 같은 색을 두 배경에 쓰면 한쪽에서 대비 부족)

## 5. 아트 타일 — 해시로 만드는 결정적 시각 요소

**파일: `app.js`의 `artTile(entry)`**

앨범아트 데이터가 없으니 엔트리 `id` 문자열을 해시(`h = h*31 + charCode`)해서 HSL 색상각을
뽑고, 그라디언트 + 제목 첫 글자로 타일을 만든다. 핵심 성질은 **결정성** — 같은 id는 영원히
같은 색. `Math.random()`을 안 쓰는 이유가 `recommend()` 때와 같다(재현 가능해야 신뢰됨).
`h*31`의 31은 문자열 해시의 관례적 소수(자바 `String.hashCode`와 같은 계열).

✋ 체크: 박정현 타일이 새로고침할 때마다 색이 바뀐다면 코드 어디가 잘못된 것인가?

## 6. 모션과 접근성 — 넣은 것보다 뺀 것

- 카드 hover 시 1px 상승 + 그림자, 섹션 로드 시 순차 fade-in **1회만**. 그 이상은 안 넣었다 —
  과한 모션은 오히려 AI 생성 티를 낸다(design_plan.md "피해야 할 것").
- `@media (prefers-reduced-motion: reduce)`에서 전부 끔 — OS의 "동작 줄이기" 설정 존중.
- 모든 포커스 가능한 요소에 `focus-visible` 아웃라인 — 키보드 사용자용.
