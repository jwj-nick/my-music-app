**Live:** https://jwj-nick.github.io/my-music-app/ · **Repo:** https://github.com/jwj-nick/my-music-app

## 작업 방식 — 학습 우선
이 프로젝트는 결과물만큼 "만드는 과정을 완전히 이해하는 것"이 목표다. 자율진행(Claude가 알아서 빠르게 다 만드는 것)을 쓰지 않는다. 마일스톤마다 아래 순서를 지킨다.

1. **개념 설명** — 이번 마일스톤에서 새로 쓰는 개념을 먼저 설명한다. 이미 아는 것(다른 프로젝트에서 써본 것)은 짧게 확인만 하고 넘어간다.
2. **함께 구현** — 코드를 같이 짜거나, Claude가 짠 걸 Nick이 줄 단위로 읽고 이해한다.
3. **확인** — `learning_plan.md`의 체크 질문에 답하거나, 직접 브라우저/폰에서 눈으로 동작을 확인한다.
4. **통과 후 다음 마일스톤** — 확인이 끝나야 다음 마일스톤으로 넘어간다. 급하게 건너뛰지 않는다.

**Phase 순서를 이렇게 잡은 이유:** 기능(1) → AI(1.5) → 디자인(2) 순서인 건, 껍데기(디자인)를 입히기 전에 알맹이(기능)가 먼저 확실히 동작해야 하기 때문이다. AI 연결(1.5)을 디자인보다 먼저 둔 이유는, 앱에 새로운 종류의 상태(API 키·외부 API 호출)가 추가되는 쪽을 먼저 안정시키고 나서 그 위에 디자인을 입혀야 나중에 다시 손대는 일이 줄기 때문이다. 이 순서는 Phase 1을 끝내고 실제로 되짚어보면서 바뀔 수 있다 — 지금은 계획이지 확정이 아니다.

## 왜 APK 패키징을 두 번 하는가
하드웨어 검증에서 브링업을 끝까지 미루지 않고 초기 샘플로 먼저 실기 검증하는 것과 같은 이유다. Phase 1이 끝나자마자 한 번 러프하게 APK로 감싸서 실제 폰에 설치해보면, "패키징 과정 자체에서 뭐가 깨지는지"를 초반에 발견할 수 있다. 이걸 Phase 2(디자인)까지 다 끝난 뒤에 처음 시도하면, 문제가 생겼을 때 원인이 기능 코드인지 디자인 코드인지 뒤섞여서 디버깅이 어려워진다.

**스마트 기능 기획 (decisions.md #29~33):** 원칙 = "사용자는 선택하고, 쿼리 문장은 앱이 조립한다".
- **답 4유형(#31)이 설계의 뿌리** — T1 플레이 링크(→골라서 엔트리화, #32), T2 지식(→카드 메모), T3 추천 후보(→"+추가" 엔트리화), T4 요약 브리핑(→읽고 소비, 관심 항목 승격). 유형마다 출력 계약과 데이터 행선지가 다르다.
- **쿼리 빌더**: Step1 답 유형 → Step2 대상(데이터에서 자동 생성) → Step3 유형별 조건(형태/기간/지역/개수) → Step4 자유 한 줄(선택) + 완전 자유 모드 별도(#30). 조립된 문장을 **전송 전 미리보기로 보여주고 수정 가능**. 기간은 절대 날짜로 변환, "추측 금지·출처 필수" 명시.
- 재료: `tasteProfile()`(1.5.6 완료) + 제외 목록 + 유형별 출력 계약. 스키마에 `links` 필드 추가(#33).
